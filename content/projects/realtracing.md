This is like the 5th time I've done raytracing, but now it's different; I'm abandoning the largest optimization ever conceived in the field of raytracing, and ignoring the Helmholtz reciprocity principle.

This came from a number of ideas I had:

- There should be a ray tracer that *doesn't* work in reverse
- It would also output a lot more information than just color
    - It would output every ray, bounce, normal, material, lighting calculation, and other such things
    - You could query this data; say, get every ray that hit a certain triangle
        - haha what if you put this in a SQLite database?
- It could be used to demonstrate the principles of ray tracing, showing the journey of a ray from actual results, not just an example for a visualization
- You could also maybe use it for lightmap baking
- Since it's not for realtime, there's less things to consider

## What I made

- A compute shader that traces one (1) ray (`glsl/the_shader.glsl`)
- A Python script (`main.py`) runs it in batches and writes the outputs to `results.bin`
- We need consistent data structures between Python and GLSL, so all structs are put in `struct_def.h`, which are translated into NumPy DTypes (`structs.py`), GLSL structs `glsl/structs.glsl`, and C headers `structs.h`
    - The program to do this is `structgen.py`, which was partially written by Claude (sorry) since I really don't care about writing this (although I did start it and wrote most of it)
    - This program accounts for the GPU's `std430` struct alignment (by adding padding fields), which is done automatically with GLSL, but needs to be corrected for in Python and C
- We also need a scene, which includes a list of triangles, materials, and (soon) BVH nodes
    - The compute shader's input data comes from `input.bin`
        - `input.bin` follows the `s_Input` struct in `structs.h`, `dtype_Input` in `structs.py`, etc.
        - The input data is not directly provided in GLSL. `main.py` splits it up into different buffers so that we can have variable-sized arrays in the shader
            - There are currently buffers for the scene data (`s_Scene`), triangle list (`s_Triangle[MAX_TRIANGLES]`), and BVH node list (`s_BVHNode[MAX_BVH_NODES]`)
            - We need variable-sized arrays, opposed to fixed-sized arrays + a `count` variable, because when iterating over a fixed-sized array the compiler will unroll the loop potentially millions of times, which of course doesn't work
            - Using a variable-sized array means that the compiler cannot know how large it is, and therefore preserves the loop
    - `inputs.bin` is generated by `scenegen.py`, which takes an OBJ file
    - Running `make scene.obj` will use the Blender CLI to export `scene.blend` to `scene.obj` (and `scene.mtl`)
        - This is what `blender_export_script.py` is for
    - Running `make inputs.bin` will generate the OBJ and run `scenegen.py`
- We need a way to see our data. This is what `cvis` is for
    - (It's called `cvis` because it's a visualizer written in C since the first version was in Python and was slow)
    - `cvis/cvis` reads `results.bin` and shows a visualization
    - It currently is not very versatile; to change things (eg. show/hide rays) you have to change the code and recompile it
    - I won't go into how it works since it is likely to change

## How to run it

Unlike most of my projects, this is actually quite accessible to run (on Linux).

1. Get the code
2. Install [uv](https://docs.astral.sh/uv/) and Blender
    - If you don't want uv you can install the Python packages found in `pyproject.toml` and change `uv` to `python3` in the `Makefile`
        - I implore you to use uv in your own projects. It makes package and environment management so simple
    - You also need `make` and `gcc`, but I consider those standard packages everyone should have
3. (Optional) Edit `scene.blend`
4. (Optional) Edit `main.py`
    - This isn't ideal, but to change the number of results you get, you have to change `N`, `CHUNKS`, and `CHUNK_SIZE` in `main()`
        - `N` is not needed if you manually set `CHUNKS` and `CHUNK_SIZE`; otherwise `CHUNK_SIZE = N // CHUNKS` (`N` is unused elsewhere)
5. Run `make results.bin`
6. (Optional) Edit `cvis/cvis.c` to change what is drawn
7. Run `make cvis/cvis` to build `cvis`
8. Run `./cvis/cvis` to see the results
9. Feel disappointed because it's quite boring
